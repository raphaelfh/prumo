## 1. Problem

| Slice | Problem on `dev` |
|---|---|
| Dev tooling | `.claude/launch.json` had a `frontend-attach` entry and `autoPort` on `frontend`/`backend`. Its `full-stack` entry ran `make start`, which `preview_start` cannot track by port. `vite.config.ts` hard-coded port 8080, so a second worktree could not take another port. |
| A. Worklist progress | PostgREST caps a select at 1000 rows and truncates silently. `loadProjectArticles`, `loadExtractionTableArticles` and `fetchProjectArticles` (`frontend/services/articlesService.ts`) read unpaged, so article 1001 onward was dropped. `useArticleExtractionValues` read every instance unpaged from the browser and sent every instance id and run id in one `.in()` URL. | B. Section rail | Collapsing the rail (`⌘\`) removed it, taking the section statuses and the jump control with it. |
| C. Active section | An `IntersectionObserver` picked the most visible section, so a tall section outvoted the one being read. `scrollIntoView` also scrolled the `overflow: hidden` ScrollArea root: one click on the last section moved it 665px and pushed the sticky rail to -616px. |
| D. Pager keys | `J` / `K` paged articles; the help copy read "Next / previous article", the reverse of the header chevrons. The diff's `[` / `]` never fire where those keys need AltGr/Option (§D). |

- (c) items the ledger rules out: offset-paging duplicates or skips when articles are inserted mid-read; a time or page cap on paging; tooltips for the compact rail on touch; a fixed 120px anchor regardless of pane height. Progress is a display aggregate that refetches.
- Fixing layout reachability for all shortcuts (AltGr/Option layouts, including `[` / `]`, `⌘\`, `g h`, …) — tracked as a separate task.
- No new DB index and no migration in this run. The plan records the >1000-instance timing (R8) only; an index, if that timing calls for one, is a follow-up. The DEBUG CORS rule already accepts any loopback port (`backend/app/core/config.py:66` `cors_origin_regex`).

- `articlesService.selectAllProjectArticles` stays on PostgREST: CLAUDE.md "app-schema reads other than extraction still use PostgREST" grandfathers `articles`. The §VI ruling covers only the worklist progress reads.
- Other pre-existing browser `extraction_*` reads stay as they are — tracked as a separate task: `frontend/hooks/extraction/helpers/getModelChildSections.ts:32`, `frontend/services/extractionInstanceService.ts:103`, `frontend/services/extractionFieldService.ts:133,138`, `frontend/hooks/extraction/helpers/queryEntityTypes.ts:17`, `frontend/services/qaTemplateService.ts:62`. - QA dashboard states that R38 does not name stay as on `dev`: the figures while its template list loads, and the figures with no active QA template.
- No change to `computeRowProgress` / `scopedRowProgress`. Progress still runs client-side, against the live template schema (`docs/reference/extraction-hitl-architecture.md` "read live").

**R9.** Merge rule, mirroring `frontend/lib/extraction/articleValues.ts` `buildArticleValueMap`:
- For each `(instance_id, field_id)`, the caller's reviewer state wins. It is joined to its CURRENT `extraction_reviewer_decisions` row through `current_decision_id`; older, superseded decisions on the coordinate are ignored. A `reject` decision does not win. Any other decision resolves with the same semantics as `run_lifecycle_service._resolved_reviewer_values` (`backend/app/services/run_lifecycle_service.py:535-587`). An `accept_proposal` decision stores `value = None` (`extraction_review_service.py:129,169,207`), so it resolves to the referenced proposal's `proposed_value` through `proposal_record_id`. Every other decision resolves to the decision row's `value`. The resolved value wins only if it is filled; a resolved empty value falls through to the next bullet.
- Otherwise the caller's newest `source='human'` proposal wins (ordered by `created_at` desc, then `id` desc), skipping empty ones.
- Emptiness is `app.services.value_semantics.is_value_empty`. **Deliberate change from the client rule:** a value carrying `absent_reason` counts as filled, justified by constitution §IX (a "no information" outcome is a recorded proposal, not a silent drop). The client's `unwrap` treated `{value: null, absent_reason}` as empty.

**One implementation (chosen).** The per-decision resolution is extracted from `_resolved_reviewer_values` into a pure function `resolve_reviewer_value(decision: str, value: Any, proposed_value: Any) -> Any | None` in `backend/app/services/value_semantics.py`. It returns `None` for `reject`, and for an empty resolved value. Otherwise it returns `strip_verification` of `value`, or of `proposed_value` when `value` is `None`. `_resolved_reviewer_values` is refactored to call it, passing `proposal_values.get(proposal_record_id)`, and its behaviour is unchanged. `article_progress_service` calls the same function. Layering allows exactly this (`scripts/fitness/check_layered_arch.py:8-10`): repositories may not import services, so the repository returns raw rows only. Its value read LEFT JOINs `extraction_proposal_records` on the decision's `proposal_record_id` to carry `proposed_value`. Because both callers share one function, no parity test is needed; the existing `run_lifecycle_service` tests guard the refactor.
